Section 1

Support Tiers

CWI AI uses a three-tier support model to resolve issues at the lowest cost and fastest speed possible. Each tier attempts resolution before escalating upward.

Tier 0
AI / Self-Serve

The client handles it themselves using embedded documentation, chatbot help prompts, FAQ pages, or the onboarding quick card. No human involvement required.

  • Refreshing or reopening the chat widget
  • Checking calendar sync settings
  • Reviewing the quick card checklist
  • Reading the bot FAQ or help prompts
Tier 1
Client Admin

A designated admin at the client's business investigates and attempts the self-serve fix steps documented in this playbook before contacting CWI AI.

  • Running through the 60-second checklist
  • Checking Calendly/Google Calendar permissions
  • Confirming Make scenario is active
  • Documenting what was tried before escalating
Tier 2
Brian — CWI AI

Brian investigates and resolves the issue. Triggered only when Tier 0 and Tier 1 steps are exhausted. Clients email brian@cwiai.net with a complete ticket including all required fields.

  • API key rotation or quota issues
  • Make/automation flow repairs
  • Bot retraining or knowledge base update
  • Calendar or webhook configuration fix

Section 2

Service Level Agreements

Priority levels apply from the moment a complete ticket (all required fields) is received at brian@cwiai.net. Response times are best-effort for a solo operator; P1/P2 are treated as drop-everything events.

Priority What it means Example First Response Target Fix
P1 Critical Total system outage — core AI/automation completely non-functional for all users Chatbot widget gone, all bookings failing, OpenRouter returning no responses Within 2 hours Same day / 4 hrs
P2 High Major function broken — significant impact on business operations Calendar not saving bookings, double-bookings occurring, automation stopped silently Within 4 hours Same day / 8 hrs

Section 3

Issue Playbooks

Expand any issue below for a complete runbook: symptom, likely cause, numbered self-serve steps, and escalation trigger. Work top-to-bottom before contacting Brian.

A — Chatbot Issues
A1 Chatbot Not Responding
Symptom
Chat widget loads but sends no reply, or spins indefinitely after user message is submitted.
Likely Cause
OpenRouter API quota exceeded or key invalid; Voiceflow/Botpress project unpublished; network block on embed domain.
Self-Serve Fix Steps
  1. Hard-refresh the page (Ctrl+Shift+R / Cmd+Shift+R) and test again.
  2. Open browser DevTools → Network tab. Send a message and look for any 401, 403, or 429 error on the API call.
  3. Log into OpenRouter dashboard. Check usage vs. quota limit. If near limit, add credits.
  4. Log into Voiceflow or Botpress. Confirm the project is Published (not Draft).
  5. Check if the embed domain is on an allowlist — add it if missing.
  6. Test on a different browser or incognito window to rule out extension conflicts.
Escalate to Tier 2 if Steps 1–6 did not resolve it, API shows no errors but bot still silent, or the issue is affecting multiple clients simultaneously.
A2 Wrong Answers / Hallucinations
Symptom
Bot confidently states incorrect pricing, hours, services, or invents information not in the knowledge base.
Likely Cause
Knowledge base outdated; system prompt missing guard-rails; model temperature set too high; no fallback instruction for unknown questions.
Self-Serve Fix Steps
  1. Screenshot the exact question and wrong answer (needed for ticket).
  2. Log into Voiceflow/Botpress. Navigate to the Knowledge Base or FAQ block that should cover this topic.
  3. Verify the correct information is present and up to date.
  4. Check the system prompt — confirm it says "Only answer from the provided knowledge base. If unsure, say you don't know."
  5. Test the same question again in the bot preview after saving.
Escalate to Tier 2 if Knowledge base is correct but bot still hallucinates, or the wrong answers are appearing on topics that were never in scope. Include the screenshot and exact phrasing.
A3 Chatbot Too Rigid / Stuck on Script
Symptom
Bot repeats the same menu options regardless of what the user types, ignores freeform input, or loops back to start.
Likely Cause
Flow is button-only with no NLP/intent fallback; AI step is missing or bypassed; "else" path not configured.
Self-Serve Fix Steps
  1. Open the flow in Voiceflow/Botpress and inspect the main menu step.
  2. Check whether there is an "Other / I typed something" branch or AI fallback step.
  3. If the flow is button-only with no else path, note this for the ticket — it requires a flow redesign.
  4. If an AI step exists, verify it's connected (not orphaned) and has a valid model selected.
  5. Add a simple fallback message: "I didn't quite get that. Can you choose one of the options above or type your question?"
Escalate to Tier 2 if The flow needs an NLP redesign or new AI intent step added — this is a configuration task beyond client admin scope.
A4 No Human Handoff Path
Symptom
Users cannot reach a human; bot has no "Talk to a person" option or the escalation button does nothing.
Likely Cause
Human handoff step was never built, webhook is misconfigured, or the step is present but not reachable from the main flow paths.
Self-Serve Fix Steps
  1. Search the flow for a "Speak to human", "Live agent", or escalation block.
  2. If it exists, trace the path — is it reachable from the main menu? Add a button if not.
  3. Test the button. It should either send an email notification or trigger a Make webhook.
  4. Check that the destination email or Make webhook URL is still valid.
  5. If no handoff exists at all, document this as a feature request in the ticket.
Escalate to Tier 2 if The handoff block is present but the webhook is broken, or no handoff was ever configured and one needs to be built.
A5 Chat Widget Not Appearing on Website
Symptom
The chat bubble or iframe does not appear on the live website even though it worked before.
Likely Cause
Embed script removed during a site update; Content Security Policy blocking the script domain; browser caching old version without the script.
Self-Serve Fix Steps
  1. View page source (Ctrl+U) and search for "voiceflow" or "botpress" — confirm the embed script is still present.
  2. If missing: your website editor may have removed it during a theme update. Re-paste the embed code into the site's header or footer section.
  3. Open DevTools → Console. Look for CSP errors mentioning a blocked script domain.
  4. If CSP is blocking it, add the chatbot domain to your site's allowed script sources.
  5. Clear browser cache and test in a private window.
  6. Test on mobile to confirm it's not a desktop-only CSS hide rule.
Escalate to Tier 2 if Embed script is present, no CSP errors, widget still invisible — may need a CSS/z-index fix or domain allowlist change in Voiceflow/Botpress settings.
B — Scheduling / Calendar
B1 Booking Not Appearing in Calendar
Symptom
Client or customer books via Calendly/booking link but the event never appears in Google Calendar or the business's calendar app.
Likely Cause
Calendly–Google Calendar integration disconnected (token expired); wrong calendar selected; Make webhook not forwarding the booking event.
Self-Serve Fix Steps
  1. Log into Calendly → Integrations → Calendar. Confirm Google Calendar shows "Connected."
  2. If it shows "Reconnect needed," click reconnect and authorize again.
  3. Confirm the correct calendar is selected under "Add to Calendar" and "Check for Conflicts."
  4. Make a test booking using a personal email and wait 2 minutes. Check the target calendar.
  5. If using Make: open the scenario, check the last run, and look for errors in the Google Calendar module.
Escalate to Tier 2 if Calendly shows connected but events still don't appear after a test booking, or Make scenario is throwing a Google API error.
B2 Double-Bookings Occurring
Symptom
Two or more customers are booked for the same time slot, or staff member shows occupied on personal calendar but available in Calendly.
Likely Cause
Calendly "Check for Conflicts" not reading all required calendars; personal calendar not connected; buffer times not set; multiple event types sharing the same availability pool.
Self-Serve Fix Steps
  1. Calendly → Integrations → Calendar Connections. Confirm all calendars used by this staff member are listed under "Check for Conflicts."
  2. Add any missing personal/work calendar to the conflict check list.
  3. Go to the event type → Availability → confirm buffer time before/after is set.
  4. If multiple event types share one host, confirm "Limit new events per day" is configured.
  5. Make a test booking to a previously affected time slot and verify it now blocks correctly.
Escalate to Tier 2 if All calendars are connected and conflict-checked but double-bookings persist — may require Calendly team scheduling or API-level review.
B3 Calendar Permission Errors
Symptom
"Insufficient permissions," "Access denied," or "403" errors when Calendly or Make tries to write to Google Calendar.
Likely Cause
OAuth token expired or revoked; Google account password changed invalidating the token; calendar sharing permissions changed by IT/admin.
Self-Serve Fix Steps
  1. Calendly → Integrations. Disconnect the Google Calendar connection completely.
  2. Go to Google Account → Security → Third-party apps. Revoke Calendly access.
  3. Return to Calendly and reconnect — sign in fresh and grant all requested permissions.
  4. If using Make: open the Google Calendar module, click the connection, and re-authorize.
  5. Run a test scenario in Make to confirm the 403 is resolved.
Escalate to Tier 2 if Re-authorization still returns 403, or the Google Workspace admin has restricted OAuth app access and it needs to be whitelisted at the domain level.
C — Make / Automation
C1 Automation Stopped Running
Symptom
A Make scenario that previously ran automatically has stopped triggering. No emails sent, no calendar events created, no CRM updates.
Likely Cause
Scenario deactivated after consecutive errors; Make operations quota exhausted; trigger webhook URL changed; a module's connection expired.
Self-Serve Fix Steps
  1. Log into Make. Find the scenario. Check the toggle — is it ON (blue) or OFF?
  2. Click "History" — look at the last 10 runs. Are they all showing errors?
  3. Click the most recent error run. Identify which module failed and what the error message says.
  4. Check your Make plan's operation count for the month — confirm you have remaining operations.
  5. Click the failing module → the connection (usually a key icon). Click "Verify" or re-authorize.
  6. Run the scenario manually using "Run once" to confirm it works, then re-activate.
Escalate to Tier 2 if All connections verify OK, scenario is active, but it still won't trigger — or the error is in a custom webhook or HTTP module with a non-obvious cause.
C2 Wrong Field Mapping / Data in Wrong Place
Symptom
Data is being created but in the wrong fields — e.g., customer name appears in the notes field, phone number goes to email, or CRM record is blank.
Likely Cause
The source app changed its field structure (common after app updates); a Make module was re-mapped incorrectly; the input form added/renamed a field.
Self-Serve Fix Steps
  1. Open the scenario in Make. Click the destination module (CRM, Google Sheets, etc.).
  2. Review each field mapping. The left side is the destination field; the right side is the source variable.
  3. Submit a fresh test entry through the trigger (form, webhook, etc.).
  4. In Make, go to History → the test run → expand the destination module output. Compare expected vs. actual values.
  5. Correct any mismatched mappings and run again manually to confirm.
Escalate to Tier 2 if The source data structure changed significantly (e.g., a form was rebuilt) and the entire scenario needs remapping, or variables are missing from the available data bundle.
D — AI Backend / OpenRouter
D1 AI Responses Stopped / API Errors
Symptom
Bot sends a message but never gets an AI response. OpenRouter returning 401, 402, 429, or 500 status codes in network requests.
Likely Cause
401 — API key invalid or revoked
402 — Account out of credits
429 — Rate limit hit (too many requests/min)
500 — OpenRouter or model provider outage
Self-Serve Fix Steps
  1. Check status.openrouter.ai — confirm no active incident.
  2. Log into OpenRouter → Keys. Verify the key used by the bot is active (not deleted or rotated).
  3. Check your OpenRouter credit balance. If $0 or negative, add credits.
  4. If 429: check if the bot has a rate limiting setting. Add a delay or reduce concurrent requests.
  5. If 401 after confirming key is correct: regenerate the key, update it in Voiceflow/Botpress, and test.
  6. If 500 and status page shows an incident: wait 15–30 minutes and retest.
Escalate to Tier 2 if Credits are sufficient, key is valid, no status incident, but 401/500 persists — key may need to be rotated at the CWI AI account level, or the model being used has been deprecated.

Section 4

Escalation Requirements

Every ticket sent to brian@cwiai.net must include all six fields below. Incomplete tickets will be returned asking for the missing information, which delays resolution.

🏢

Business Name

Your full business name as registered with CWI AI. Helps identify your bot config instantly.

🔍

What Broke

Plain-language description. "The chat widget stopped responding after we updated our website." Be specific.

🚨

Priority (P1–P4)

Self-assess using the SLA table. State why you chose this priority if P1 or P2.

🔧

Steps Already Tried

List each step from the playbook you completed. "Tried A1 steps 1–5. Step 3 showed a 429 error."

📸

Screenshot or Screen Recording

Attach the error message, broken UI state, or DevTools console output. No screenshot = slower diagnosis.

🕐

When It Started

Approximate date and time (with timezone). "Started failing around 2pm CST on June 7th." Any changes made just before?

Section 5

Maintenance Routines

Proactive maintenance catches issues before clients notice. These routines apply across all CWI AI managed deployments.

As Needed
Bot Retraining
  • Client submits updated FAQs, pricing, or service list
  • Open Voiceflow/Botpress knowledge base
  • Update or replace outdated content blocks
  • Update system prompt if scope changed
  • Run 10 test questions covering changed topics
  • Publish updated flow
  • Confirm widget reflects changes on live site
  • Notify client retraining is complete
Weekly — 5 min
Weekly Health Check
  • Open each client's bot and send 2–3 test messages
  • Confirm responses are accurate and fast (<3 sec)
  • Check Make scenario history — 0 errors this week?
  • Glance at OpenRouter credit balance — add if under $10
  • Confirm Calendly is still connected to calendar
  • Log any anomalies in client notes
Monthly
Monthly Review
  • Review OpenRouter usage report — note top models used
  • Check Make operation usage vs. plan limits
  • Review Calendly booking volume per client
  • Rotate API keys if any are 90+ days old
  • Update this playbook with any new issue types found
  • Send client a brief "your AI this month" summary
  • Check for platform updates (Voiceflow, Botpress, Make)
  • Schedule any pending bot retraining sessions
